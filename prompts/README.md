# Evaluation prompts, verbatim

Generated by `scripts/dump_prompts.py` from the running agent, not transcribed. Regenerate
with `make prompts`; `--check` fails if these files drift from the code.

The system context is four messages, in this order:

| # | File | Varies by runtime? | Varies with the cap? |
|---|---|---|---|
| 0 | `00_system_prompt.txt` | no | no |
| 1 | `01_runtime_banner_{persistent,reset}.txt` | **yes** | no |
| 2 | `02_fewshot_{persistent,reset}.txt` | **yes** | no |
| 3 | `03_tool_prompt_cap25.txt` | no | **yes** (the integer in `STRICT LIMIT`) |

The task goal is identical across conditions and arrives as the first *user* message; it is
generated per instance and ships with the task definitions, not here.

Two things a reviewer auditing the paper's stated confound will want:

- The banner (1) and the few-shot block (2) are what make the persistent-vs-stateless
  contrast *bundled*: the runtime semantics and the prompt change together. The appendix
  says so, and this is where you check it.
- Sweeping the cap within a cell changes only file 3, and only the integer in its last
  line, which is why the within-cell dose-response is a clean manipulation. The same
  integer is echoed back in the runtime's cap error.
